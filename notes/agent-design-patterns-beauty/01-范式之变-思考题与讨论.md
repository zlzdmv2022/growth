## 二、思考题参考答案（从留言区讨论提炼）

> 本课"没有标准答案"。以下按 5 道题把留言区散落的讨论逐题提炼成参考答案：观点归属各留言作者，作者确认处均已标注；少量综合推断以「提炼」口吻呈现，可对照第三节原文复核。

### Q1：三代演进的根因（决策权搬家 + 高不确定性）是否到位？

**提炼答案：根因成立，但留言区给出了四处精度修正。**

| 修正 | 来源 | 要点 |
|---|---|---|
| 叠加而非替代 | 111（23 赞）· 作者"完全同意" | Agent 底层仍跑在分布式基础设施上，代码仍需 GoF 组织（只是不再是决策主体）；Agent 越复杂，容错/监控/日志/审计要求越高。作者定调："传统软件工程反而更重要了，因为复杂度是叠加，而不是替代。" |
| "断裂"实为"范围变化" | G东西环绕着我 · 作者确认 | 任何结论生效都有前提；"断裂"是作者故意选的吸引眼球的强说法 |
| 三代是三种"组合单元"，未来三层并存 | xdcrazyboy 提问 · 作者解答 | Gen1 回答对象怎么组合 / Gen2 服务怎么协调 / Gen3 agent 怎么协作；未来 Gen3 作外壳、Gen2 居中、Gen1 在底层 |
| 勘误"在设计时"→"在运行时" | 土豆 · 作者确认 | 决策权搬家的准确表述是运行时决策 |

**深刻之处的前提佐证**（yphust · 2 赞）：控制论、统计学、法律、保险、航空都证明"伟大的工程建立在对不确定性的驯服之上"——"高不确定性"作为根因跨学科成立，且作者指出 Harness 与 CAP 权衡有"天然血缘相似性"。

### Q2：GoF 模式自检 —— 项目里用得最多的模式及其核心假设

两位读者交卷 + 一条同构发现，正好覆盖了最常见答案：

| 来源 | 最常用模式 | 核心假设 → Agent 时代如何失效 |
|---|---|---|
| Cassie（3 赞 · 前端视角） | 单例、工厂、观察者、访问者 | 单进程、同步、类型编译期已知 → 作者确认设计反转："结构定义完 ≠ 行为确定，结构只能提高稳定概率" |
| 白泽（后端视角） | 单例、抽象工厂、观察者、装饰器 | 同上；作者补充 Agent 高频接替者：上下文筛选与压缩、工具调度、规划执行、进度追踪、护栏三明治 |
| PatrickL（40 赞 · 置顶同构） | 观察者→单例→策略→工厂 | 四模式恰好构成 OODA 闭环（Observe→Orient→Decide→Act）；作者确认"这就是 Harness 核心"，但同步推送/全局状态/人选策略/静态生产四大假设逐一断裂 |

**Singleton 断裂的最深展开**（LL.Chen 长干货 · 作者回复）：Agent 时代不能再假设"全局状态随时共享"——状态会被 context window 切片、压缩、遗忘、迁移，所以记忆必须拆层：Working Memory（真正被送进模型的 token）→ Short-term Memory（session 状态与历史摘要）→ Long-term / Procedural Memory。Singleton 的接替者是 MemoryArchitecture。

### Q3：分布式模式自检 —— 生产系统不可或缺的是哪几个？

**如实说明：留言区没有读者按题直接作答。** 但两条作者回复 + 一份书单给出间接答案：

- **状态同步四层方案**（回复 AIKO Nexus · 7 赞 · 置顶）：Pull-on-demand / Periodic refresh / **Event-driven invalidation**（消息队列 / webhook / CDC）/ Hybrid 冷热分层——事件驱动失效正是分布式时代的 pub/sub 遗产，Agent 的感知与记忆同步直接复用这套分布式模式；
- **"返回硬上限"**（回复 Geek_23ba06 的 L3 方案）：超限自动截断 + 挂 handle，提炼即分布式模式里的背压/限流思想——不是消失，而是下沉为 Harness 结构；
- **第二代书单**（回复 Porter Zhang · 14 赞）：《Building Microservices》《Microservices Patterns》《Cloud Native Patterns》《DDIA》《SRE》——Gen2 模式仍是生产 Agent 系统的"存活层"，不可或缺。

### Q4：GoF 断裂自检 —— 关键类改造成 Agent 版本，先碰哪种断裂？

**最完整的实战作答是 Geek_23ba06 的 ELK 案例**（4 赞，作者五级方案回复）——一次命中两大断裂：

- **Observer 断裂（主爆点）**：主 agent 直接 elk_query 查日志 = 海量事件流全推上下文，占满窗口、频繁触发压缩——"同步推送自爆"的活标本；
- **Singleton 断裂（次生）**：写在 AGENTS.md 的"用子 agent 执行"规则被压缩丢掉，模型故态复萌——全局可共享状态的假设失效。

**作者五级解法（软 → 硬）**：L1 写 AGENTS.md（劝模型）→ L2 移进每轮重注入的 P0 区 → L3 工具返回硬上限 → L4 pre-tool-use hook 拦截 → L5 主 agent 不暴露 elk_query。落地方案：只给主 agent `investigate_logs(query, time_range, service)`，spawn 便宜模型 sub-agent 独占原始日志、只回传 200–500 token 摘要。"这条规则不再需要模型去记得遵守，因为它已经变成架构的一部分。"

**辅助数据点**：爱海贼的无处不在（11 赞）Java 注释四板斧（skills 自动检测 / 规则文件 / hooks 检查 / subagent 编排），作者定调"可检测、可修复、可回撤、可复验"；LL.Chen 的记忆四层拆分（状态被切片/压缩/遗忘/迁移）。

### Q5：Harness vs Prompt 优先级 —— 本讲唯一有作者确认答案的题

**答案：选 (b)，改 harness。轩爷的回答获作者回复"这就是正确答案"：**

> **轩爷**：我选 B。prompt 调用 LLM 的结果存在不确定性，虽然可以写出严格规范的 prompt 对 LLM 输出进行约束，但每次这么干，等于越来越负重前行。harness 从权限、上下文、hooks、工具、记忆等多方面对 LLM 运行时进行约束，让我想要的，无需过多人工干预，就能得到有边界限制的结果，属于轻装前行。

三条留言互相印证：

| 留言 | 论据 |
|---|---|
| 轩爷（作者确认正确答案） | prompt 约束 = 负重前行；harness 约束 = 轻装前行 |
| 爱海贼的无处不在（11 赞） | prompt 在自己环境好使、别人电脑未必；从 harness 机制做交付才稳定。作者："Prompt 告诉模型该怎么做，Harness 解决即使模型没完全按预期做，系统也能把结果拉回正轨。" |
| Geek_23ba06（4 赞） | L1 写规则 = 劝模型（压缩后就忘）；L3–L5 = 模型绕不过去的结构 |

题面本身已把选项定义为"(a) 这次别犯错" vs "(b) 永远没机会犯错"；作者对轩爷答案的确认，就是本讲的工程立场：**把"期待模型听话"换成"设计模型绕不过去的结构"。**

## 三、高分评论及作者回复（按点赞数排序）

### 🥇 1. PatrickL（40 赞 · 置顶）：GoF 四模式与 OODA 环同构

> **PatrickL**：发现了同构之美~
> GoF：观察者模式 → 单例模式 → 策略模式 → 工厂模式
> OODA 环：Observe → Orient → Decide → Act

**作者回复**：PatrickL 兄弟渊博。先说啥是 OODA 环——它是经典决策闭环模型，最早来自美国空军上校 John Boyd 的军事决策思想：看见变化 → 理解局势 → 做出选择 → 采取行动，再观察新结果，继续循环。在《Designing AI Agents》中我详细拆解了从 OODA 环到 ReAct 再到 Agentic Loop 的进化线。人、军队、企业、软件系统、AI Agent，只要面对不确定环境并持续行动，都绕不开这个环——**这就是 Harness 核心**。

从观察者 → 单例 → 策略 → 工厂，真的可以看成一个对象系统里的运行闭环：

| GoF 模式 | 环节 | 作用 |
|---|---|---|
| 观察者模式 | Observe | 感知变化——谁变了、谁需要被通知 |
| 单例模式 | Orient | 稳定的状态锚点 / 全局上下文，把观察到的信息放进已有上下文理解 |
| 策略模式 | Decide | 从多个可替代方案中选择行动路径 |
| 工厂模式 | Act | 生成执行对象、落地行动结构 |

### 🥈 2. 111（23 赞）：三代模式是叠加，不是替代

> **111**：虽然内容里提到"第二代不是推翻第一代，第三代也不是推翻第二代"，但论述中 GoF 和分布式模式显得"失重"了。实际上：Agent 系统底层仍然运行在分布式基础设施上；Agent 的代码仍需要 GoF 模式来组织（只是不再是决策主体）。甚至可以说 Agent 越复杂，对传统工程能力要求越高——容错、监控、日志、审计都更困难了。三代模式是叠加关系而非替代关系。
> 另外，未来 Agent 架构设计重心将从"功能架构"逐步迁往"约束架构"：Agent 能做什么固然重要，但 Agent 不能做什么更重要。这个趋势从 LangChain 官方 Blog 也能看出来——LangSmith 不只做监控，还要基于监控数据做问题识别、预警，甚至基于数据进一步迭代。

**作者回复**：精彩精彩！我完全同意。"**Agent 时代，传统软件工程反而更重要了，因为复杂度是叠加，而不是替代的关系。**"（作者表示暂不改动原文，供大家审视探讨，回头调整说法让脉络更清晰。）

### 4. 爱海贼的无处不在（11 赞）：Harness vs Prompt 的工程实践

> **爱海贼的无处不在**：2026 年开始提示词不够用了。同事生成代码没写 Java 注释，别人提醒在宪法或 agents.md 加提示词就行；而我会从 harness 角度增加控制：① 代码生成后触发自动检测补注释的 skills；② 针对 java 文件的特殊规则文件；③ hooks 让 AI 生成后检查是否有注释；④ subagent 机制编排补注释和文档。自己环境加提示词未必保证别人电脑也好使；从 harness 机制上做，才能让代码交付更稳定。

**作者回复**："**Prompt 告诉模型该怎么做，Harness 解决即使模型没完全按预期做，系统也能把结果拉回正轨。**" Java 注释这个例子特别典型：只靠 prompt，本质是期待模型一次性听话；用 harness，就是把"是否有注释"变成**可检测、可修复、可回撤、可复验**的工程环节。

### 5. AIKO Nexus（7 赞 · 置顶）：环境变化，Agent 怎么同步状态？

> **AIKO Nexus**：环境不确定性下，Agent 是不是应该有主动更新的同步机制，而不是每次执行任务时被动"后知后觉"用了旧信息？是外部环境变了主动触发，还是定时更新？

**作者回复**：当然需要完善的从环境不断吸收最新状态的机制。**Loop Engineering 的内核，不外乎就是判断随着情况的变化而不断的变化。** 感知模式里的渐进加载、记忆模式里的失败日记（尤其情节记忆的召回触发点）都在讲这个方向。工作流编排有四种可能：

| 机制 | 做法 | 优缺点 | 适用 |
|---|---|---|---|
| Pull-on-demand 懒拉取 | 每次任务开始现拉最新 | 简单、无过期问题；但付出查询延迟，不知道两次拉取之间发生了什么 | 低频、延迟不敏感、变化平缓 |
| Periodic refresh 定时刷新 | 状态加 TTL 过期重拉；或后台定时全量刷新（RAG 夜跑 embedding） | 延迟与新鲜度可控折中；TTL 窗口内仍是旧的 | 中等变更率 |
| Event-driven invalidation 事件驱动失效 | 上游变了主动推送事件（消息队列 / webhook / CDC） | 几乎实时；需要 pub/sub、顺序保证、处理乱序 | 高变更率 + 高影响 |
| Hybrid 混合 | 按数据冷热分层 | 热数据→Event-driven；温数据→Periodic refresh；冷数据→Pull-on-demand | 生产系统几乎都是这种 |

### 6. Geek_23ba06（4 赞）：ELK 日志挤爆上下文，模型不守规矩怎么办？

> **Geek_23ba06**：用 openCode + 自定义 elk_query 技能查 ELK 日志定位现网问题，日志量大易占满上下文频繁触发压缩。已在 AGENTS.md 写明"用子 agent 执行 elk_query"，但上下文压缩后模型会忽视规则，又在主 agent 查日志。从 harness 工程角度应该怎么做？

**作者回复**：**应该把规则从"劝模型"升级成"模型绕不过去的结构"。从软到硬五级：**

- → L1 写 AGENTS.md（你现在这层）
- → L2 移进每轮重注入的 P0 区
- → L3 给 elk_query 加返回硬上限（超了自动截断 + 挂 handle）
- → L4 pre-tool-use hook 拦截调用方
- → L5 主 agent 根本不暴露 elk_query

**建议**：主 agent 只给一个 `investigate_logs(query, time_range, service)`，内部 spawn 一个便宜模型的 sub-agent，独占 elk_query 读原始日志，只回传结构化摘要 + log handle。主 agent 的 context 永远只进 200–500 token 摘要、原始日志一行不进，sub-agent 读完即销毁。"**这条规则不再需要模型去记得遵守，因为它已经变成架构的一部分。**"

### 7. Cassie（3 赞）：前端视角的"失控感"

> **Cassie**：以前写项目逻辑用 GoF 模式很有章法（单例、工厂、观察者、访问者）；现在 aicoding 中把控不了模型生成的方式——加了一堆 MCP、skills、tools、agents.md，仍不能保证每次产出的确定性，看似定义了范式，执行结果还是有各种问题。

### 9. yphust（2 赞）：伟大的工程建立在驯服不确定性之上

> **yphust**：其他学科早就证明了一件事：伟大的工程不是建立在确定性之上，而是建立在对不确定性的驯服之上——控制论驯服动态系统，统计学驯服随机样本，法律驯服人性与权力，保险驯服风险，航空驯服高危复杂系统，制造业驯服过程波动。而 Agent 时代，Harness Engineer 要驯服的是：模型的运行时决策不确定性。

**作者回复**：Harness：如何约束、引导、隔离、放大、抑制、修正模型在运行时产生的不确定行为。"**没法让模型永远正确，而是在模型注定会犯错的前提下，依然让系统持续产生正确结果。** 这和分布式系统里的 CAP 权衡理论有天然的血缘相似性。"

## 四、更多精选问答

### ReAct 和 Harness 什么关系？（晴天了）

> **晴天了**：我认为 ReAct 是 agent 的骨架，是 agent 本身；而 harness 是束缚 ReAct Agent 用的（感知、记忆、推理、行动、反思、协作、治理）。对不对？

**作者回复**：**ReAct 是最小级别的极简 Harness。** 当你用代码完成了 ReAct 循环、做完了一个任务，你就手动实现了一个最简单的 Harness。但许多上层建筑（感知、记忆、推理、行动、反思、协作、治理）尚未被体现出来，你的 Agent 还是一个 Baby。

### 会不会有标准化、通用的 Harness？（树洞）

**作者回复**：我怀疑未来应该会有。**Claude Code 未来就有可能是通吃一切的 Agent OS。** 但这不等于 Agent OS 能覆盖地球上所有特定场景——就像你不能在汽车上装一套 Unix 或 H200。即使如此，学习 Harness 的设计思想，对驾驭未来的 Agent OS 还是有用。因此，学习吧！

### 哪些地方适合 Agent 化？判断标准（木易杨）

**作者回复**（Agent 化四判断）：

1. 大原则：项目中能 Agent 化的地方就 Agent 化，这是未来大趋势；
2. **适合**：不固定的、模糊的、没有规则的、以前需要人工的、不重要的、可以允许出错的；
3. **保持现状**：固定的、清晰的工作流、工具型部分；
4. **三思而行**：非常重要、非常 Critical 的。

### Agent 高频模式有哪些？（白泽）

> **白泽**：GoF 用得更多的是单例、抽象工厂、观察者、装饰器；Agent 里面的模式应该也有常用的几种吧？

**作者回复**：会有一组高频模式，但不能只按流行度选。现在最常见的是**上下文筛选与压缩、工具调度、规划执行、进度追踪和护栏三明治**。真正的起点仍是你系统里**反复出现且代价高的失败**。

### 熔断和审批是一回事吗？（Geek_ac96f1）

> **Geek_ac96f1**：熔断关注的是故障传播，是系统自我保护机制；而审批关注的是权限，是高危操作时需要授权，跟系统健康没关系。熔断对应的概念应该是 agent loop 的失控保护。

**作者回复**：是的，你给出的对应更精准。**熔断 ↔ agent loop 失控保护，这才是结构上真正同型的映射。审批是 agent 时代真正新增的治理模式**，不是从熔断"进化"来的。硬把它跟熔断对上，反而模糊了它作为一个新原语的独立价值。

### 三代不是一个维度的东西，怎么比？（xdcrazyboy）

> **xdcrazyboy**：第一代第二代是开发各种业务和工具，第三代是开发/调教 agent，不是一个维度的东西。我们现在业务开发只是用 agent 写第一代第二代的设计模式更方便了，这个课题说的是"开发 agent 的设计模式"，不是"agent 时代开发任何东西的设计模式"？

**作者回复**：我很认可你的看法，但我们是从不同视角看问题。用 Agent 写 GoF 模式更方便——没错。但从架构设计的视角，不只是用 Agent 写代码这么简单。**Gen 1 模式回答"对象之间怎么组合"，Gen 2 模式回答"服务之间怎么协调"，Gen 3 模式回答"agent 之间怎么协作"**。它们不是三条替代路径，是三种不同组合单元的对应词汇。你的系统主要组合单元是什么，你就该主要用哪一代模式。**三代常常并存于同一个大系统：外层可能是 Gen 3 agent 编排，中间是 Gen 2 服务，底层类的结构还是 Gen 1。未来的世界将以 Gen 3 为主要上层外壳，内部有 Gen 2，底层是 Gen 1。**

### 三代层次关系再确认（Geek1254）

> **Geek1254**：由 Agent 模式来替代现有开发范式不现实，它用来驾驭大模型，让行为可预测、路径可感知、故障可排查。这个过程是加法。

**作者回复**：是的，三个完全不同的层次，有共性也有特性，是叠加关系。GoF 是代码层架构设计——永远存在；分布式是大数据时代的架构设计——我们仍处于这个时代；**Agent 是在前两层复杂度的基础上，多了一个不确定性，这个不确定性可以分布在各层级的各个角落。**

### working memory 和 short-term memory 的区别？（LL.Chen · 长干货）

> **LL.Chen**：两者看上去都在一个上下文当中，指的是 session 的 jsonl 全量信息么？区别在哪里？

**作者回复**：

- **Working Memory** = 当前 context window 里真正被送进模型的 token。即时的、临时的、容量受限的。模型这一轮能不能答对，主要取决于这些内容有没有被放进来。
- **Short-term Memory** = 这个 session 的会话状态和历史摘要。不一定全在当前 context window 里，而是存在外部状态里：session state、conversation summary、JSONL 历史、已确认过的约束等。需要时再被压缩、检索、整理后放回 working memory。

**简单理解：WM = 当前被模型"看见"的内容；STM = 当前会话中"被系统记住、但未必每轮都放进模型"的状态。** jsonl 全量历史更像 STM 的原始存储形式；真正进入模型推理的，只是被筛选、摘要、压缩后的一部分。

举例：你和 Agent 讨论代码 bug——当前 prompt 里的报错、相关函数、你刚说的要求，是 working memory；前面 20 轮确认过的"不要改数据库 schema""只能改 service 层"，可能不在当前 prompt 里，但系统仍保存在 session state 或摘要里——这就是 short-term memory，后面需要时再拉回来。

这张图想表达的是：Agent 时代不能再假设有一个 Singleton 式的全局状态随时共享；**状态会被 context window 切片、压缩、遗忘、迁移**。因此需要把记忆拆层：当前可见的 working memory、会话级的 short-term memory、可持久检索的 long-term memory、可复用的 procedural memory。（记忆模块会详细展开。）
