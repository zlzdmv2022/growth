### Q1：你的 Agent 系统最容易失控的是哪一类资源？

**提炼答案：留言区实答覆盖了至少五脉的失控案例——感知、记忆、推理、行动/流程；其中"输入失控（感知）"出现最多，恰好印证正文"生产系统最先死的往往就是 input"。**

| 失控的脉 | 来源 | 案例 | 作者回复要点 |
|---|---|---|---|
| 感知（注意力预算） | JayClock（25 赞 · 全场最高） | 编码 agent 输入失控：历史代码命名问题，导致 grep 等方式读取大量语义相近但未必有用的代码——"在链式执行的一开始就在积累错误" | 作者盛赞"这是什么水准的回答？" |
| 记忆（连续性预算） | 轩爷（5 赞） | Hermes 案例：第一天 skill 沉淀好用，第三天同一 skill 变蠢——排查是每天半夜 reset 丢了记忆连续性 | **作者确认**：周期性任务的 Memory 脉必须 "Heavy 级别"，至少 Procedural Memory + Progress Tracking + Failure Journals 三模式联手 + HITL |
| 感知+记忆+推理复合失控 | Kin | 意图识别：提示词塞满 Tool、MCP、skill + 写死的 Graph 条件路由 → 幻话频发（skill 没调起 / 工具反复调 / 多轮后跑去干别的）——"感知、记忆、推理三个失控全犯了一遍" | 修法：**用一个严格的 Schema，把 Agent 的意图带回机械的控制平面**，永远往固定目标走 |
| 推理（不确定性预算） | 有学识的兔子（4 赞） | 推理过程不透明；陌生领域"推理流程很难细化和校验"；多 agent 从不同角度审查仍觉得风险不可控 | 作者回复：这是哲学问题——"当我们自己都不是这个领域的合格裁判时，怎么信任 agent"；建议先把自己变成半个专家 + 团队必须配领域专家 |
| 感知（意图识别节点） | Bingooo（2 赞） | 越来越多业务判断塞入"轻量级"意图识别 → 越来越慢、越来越不准 | 作者用**急诊分诊**比喻：老专家要藏在分诊室后面，等着路由结果才正式会见——控制平面侧必须轻量 |
| 流程/行动（预算失守） | 梦倚栏杆（1 赞） | workbuddy 先出 UI 图、确认后直接生成前后端代码 → 各种功能点遗漏、逐点修正很恼火 | "Agent 做 Agent 的事情，控制流做控制流的事情。拆分好了谁负责干啥，基本上就无敌了" |

**提炼**：失控多为复合型，但都能映射回七脉中的某一脉预算失守；修法方向也一致——把失控的资源重新"装进预算"（严格 Schema、分层记忆落盘、轻量控制平面、人机分工）。

### Q2：你的工作流采用哪种执行拓扑？错误沿什么路径传播？

**提炼答案：三个高质量实答被作者全部确认，共同指向"看错误怎么走，而不是看流程长什么样"。**

| 来源 | 拓扑判定 | 错误传播路径 | 作者确认 |
|---|---|---|---|
| JayClock（25 赞 · 全场最高） | **HATEOAS 报销申请 Agent = 状态驱动的 Route + Loop**，不是 Chain：服务端每步只暴露当前状态允许的动作，Agent"看当前状态，再选下一步"；payload 参数校验又带出 Loop | 错误**分派**：误读状态或误解动作含义 → 外部系统状态被改变 → "后续所有可选路径也会基于这个错误状态继续展开" | **作者确认**：结合生产实践的真知灼见；"为什么是 Route + Loop 而不是 Chain"是读懂了双轴拓扑；切中 **stateful vs stateless agent 系统的根本差别**。另附 HATEOAS 学习链接 |
| mazhen（3 赞） | **Claude Code = Loop 作为运行时，内部嵌入各种拓扑**：路由结果作为输入再次 loop；Plan-and-Execute 外层还得套一个 loop 根据执行结果调整计划 | Loop 内的嵌套拓扑各自叠加自己的错误传播方式 | **作者确认**："当然肯定"——编排方式由任务特点决定，复杂系统内部"一定是有各种各样的设计理念和思路的" |
| Jason_LI（4 赞 · 产品文档/原型 Agent） | 五阶段双轴拆解：需求分析/竞品分析/需求编写 = **链式+感知+行动+推理**；四类评审 = **并行+反思**；评审反馈定点调整 = **反思+循环+治理+协作**；证据落地知识库 = **治理**；人工审核发布 = **行动** | （未单独展开错误路径，重在用双轴做阶段级映射） | **作者确认**："理解的相当到位！" |

**提炼**：真实系统几乎都是复合拓扑（Route+Loop、Loop 内嵌其他拓扑）；拓扑识别的关键是把"流程长什么样"翻译成"错误怎么移动"——这正是横轴作为 failure propagation axis 的用法。

### Q3：为什么"用了几个 Agent / 接了几个工具"不足以说明设计好坏？

**如实说明：留言区没有读者按题直接作答。** 但正文立场 + 多条问答提供了完整间接答案：

- **正文立场（作者）**：没有坐标，"我们用了一个 agent workflow"这句话几乎没有信息量；有了坐标（推理×循环 + 治理×路由）才能进入工程评审。**词汇越热，歧义越大。**
- **F-sy 置顶问答（19 赞）**：作者回复点出 90% 定律——"Agent 系统最终失败，90% 不是模型不会推理，而是错误在系统里扩散了。因为 Agent 会出错，所以设计的本质是约束。" → 数量描述不了**约束质量**。
- **Black船长 置顶问答（16 赞）**：同一个"有个分派器在派活"的外观下，Route 和 Orchestrate 是两种完全不同的错误传播路径（固定菜单选一个+决策退场 vs 临时拆菜单+中心全程在场）→ 只数 Agent 数无法区分工程后果完全不同的系统。
- **Kin 的反面案例**：工具塞得越多反而越失控 → 工具多 ≠ 设计好，反而制造幻觉。
- **mazhen 问答**：Agent 的推理 = LLM 的推理 + Harness 的推理 → 设计好坏看 Harness 编排质量，不看组件数量。

**提炼**：数量是"能力展示"的语言，双轴坐标才是"约束质量"的语言——评价系统要看它在七脉上守住了哪些资源预算、在六式上切断了哪些错误传播路径。

## 三、高分评论及作者回复（按点赞数排序）

### 1. JayClock（25 赞 · 全场最高）

> 1. 编码 agent 的输入失控，由于历史代码命名的问题，导致 grep 等方式，读取了大量语义相近但是未必有用的代码。在链式执行的一开始就在积累错误。
> 2. HATEOAS 风格接口下的 Agent 工作流，最典型的执行拓扑不是固定的链式执行，而是**状态驱动的路由**。以一个"报销申请 Agent"为例：它不是预先写死"先创建申请、再上传发票、再提交审批、再查询结果"这一整条流程，而是在每一步读取服务端返回的当前状态，以及当前状态下允许执行的动作。比如报销单处于草稿状态时，系统只暴露"编辑、上传发票、取消"等动作；等发票上传完成后，系统再暴露"提交审批"；提交之后，又暴露"查询审批状态"或"补充材料"等动作。Agent 的任务不是背完整流程图，而是根据当前状态和可用动作，判断下一步该走哪条路径。属于 Route + Loop（因为 payload 参数需要校验）。它每执行一步，都会进入一个新状态，然后重新观察当前可用动作，再次选择下一步。也就是说，它不是"一步步传下去"，而是"看当前状态，再选下一步"。这种拓扑最容易让错误沿着错误分派的路径传播。因为关键风险在于 Agent 选错了路。如果它误读了当前状态，或者误解了某个动作的业务含义，就可能把本该继续补充材料的申请提交出去，或者把"取消编辑"误认为"取消整个申请"。一旦选错动作，外部系统状态就会被改变，后续所有可选路径也会基于这个错误状态继续展开。

**作者回复**：

> 这是什么水准的回答？这是佳哥所期待的、宝贵的结合了生产实践场景的真知灼见。首先，什么是 HATEOAS Agent，大家参考下面链接学习体会 https://nordicapis.com/hateoas-the-api-design-style-that-was-waiting-for-ai/ 兄弟也挑出了一个真实的边界"报销申请 Agent，这个 Case 中，拓扑不是固定的，是由服务端状态驱动的"。说这是"Route + Loop"为什么不是 Chain（"看当前状态再选下一步"），这是读懂了双轴拓扑的。说"外部系统状态被改变，后续所有可选路径基于错误状态展开"这切中了 stateful agent 系统跟 stateless agent 系统的根本差别。为你点赞！

### 2. F-sy（19 赞 · 📌置顶）

> 请问怎么理解"这六式不是为了画图好看。它们分别对应六种错误传播方式：Chain 是错误级联，Route 是错误分派，Parallel 是错误聚合，Orchestrate 是错误分解，Loop 是错误复合，Hierarchy 是错误放大或错误隔离"。6 种拓扑结构怎么跟错误传播方式对应上的？

**作者回复**：

> 我这个结论其实是一个很深的工程观察。我写在 Designing AI Agents 书里面了。
> 我们大部分人看 Workflow，只看控制流（Control Flow）：Chain：A → B → C；Route：A → B 或 C；Parallel：A → B 和 C；Loop：A ↺；Hierarchy：Manager → Worker；Orchestrate：Planner → Executor。
> **因为 Agent 会出错，所以设计的本质是约束。因为 Agent 系统最终失败，90% 不是模型不会推理，而是错误在系统里扩散了。**
> 真正的工业设计师画 Workflow 时脑子里想的是：Chain 错误会不会一路传下去；Route 会不会分错队；Parallel 多个错误如何汇总；Orchestrate 任务拆解会不会错；Loop 错误会不会自我强化；Hierarchy 错误会被放大还是隔离。
> 怎么样，是不是很震撼！

### 3. Black船长（16 赞 · 📌置顶）

> 路由和编排的具体区别是什么？看着都是由前置的路由器/任务拆解器，进行任务分派

**作者回复**：

> 你的直觉没错，两者前端确实都像"有个分派器在派活"。差别不在前端长什么样，而在派完之后发生了什么。
>
> - **决策内容**：路由是选"走哪条已知的路"（从固定菜单里挑一个）；编排是决定"把任务拆成哪些子任务"（菜单是临时生成的）
> - **分支来源**：路由是设计时就固定好的 N 个类别；编排是运行时由输入决定，事先无法穷举
> - **中心的存活**：路由是决策一次就退场（fire-and-forget）；编排是全程在场，还要回收各步结果做综合
>
> Anthropic 的《Building Effective Agents》：Routing 是"把输入分类后导向某个预设的后续任务"；Orchestrator-workers 是"中心 LLM 动态拆解任务、分派给 worker、再综合结果"，原文特别强调"子任务不是预定义的，而是由具体输入决定的"。
> 伪代码：
>
> ```python
> # 路由 Route：一次决策，分派完就结束
> def route(query):
>     kind = classify(query)          # 唯一的一次判断
>     return HANDLERS[kind](query)    # 派给已知 handler，自己退出
>
> # 编排 Orchestrate：中心持续在场，拆解 + 综合
> def orchestrate(task):
>     state = init(task)
>     while not state.done:
>         step   = planner.next(state)    # 每一步都回到中心重新决定
>         result = execute(step)          # 子任务可能是临时拆出来的
>         state  = update(state, result)  # 控制权反复收回中心
>     return synthesize(state)            # 最后还要把结果合成
> ```

> 小明同学这个反馈特别好，但结论佳哥肯定不同意，原因如下！这是一个学术名称。"认知功能"这个词不是框架新造的，是认知科学（cognitive science）和 AI 领域几十年前就确立的技术术语。小明同学说的"对某事的看法深浅"只是这个词的一种日常用法，其实并不是它的完整意涵。

## 四、更多精选问答（与思考题间接相关或独立高价值）

### mazhen：Agent 的推理和 LLM 的推理是什么关系？

> mazhen：我想问一个很基础的问题：Agent 的推理具体指的是什么？我们知道 Agent 本身没有智能，它的能力完全来自大模型。那么，当我们说"Agent 的推理"时，它和大模型的推理是什么关系？两者是同一件事，还是有区别？

**作者回复**：

> 好问题。**Agent 的推理 = LLM 的推理 + Harness 的推理**。LLM 的推理 → 黑箱；Harness 的推理 → 可以有一些人为的编排（逐渐被 LLM 的推理吃掉，但是吃不全），如对抗-批判，循环反复（可以吃掉部分），思维链（几乎完全被思维模型吃掉），把推理分出层次。

### novoer：横轴竟然是错误传播路径轴，太开脑洞了

> novoer：这个横轴竟然不是流程图轴，而是错误的传播路径轴（failure propagation axis）。你选择了拓扑，就是在选择错误如何移动。这真是大开脑洞！不是么？确实是太惊讶了！
